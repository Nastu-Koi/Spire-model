# 采集吞吐的提速尝试

- **时间**：2026-10-17 ~ 2026-10-18
- **来源**：`.scratch/joint-training/issues/15-collector-timing.md`、`22-collector-pass-overhead.md`、`25-collector-throughput.md`、`29-iteration-time-budget.md`、`30-operator-level-speedups.md`；探针原始输出在 `.scratch/joint-training/assets/probe-25/`、`probe-29/`、`probe-30/`；提交 `f2c678d`、`3f536b3`、`525b528`；后续的编码表见 `38-encoder-content-cache.md` 与 `assets/probe-38/`
- **状态**：多数被否决。采集进程受主机发射限制，流水线、解包改写、编码器编译、多采集进程都没有提速；有效的是关系偏置并排建出、全局层 CUDA graph、程序节点字段紧凑化和引擎 32 → 48。之后（2026-10-19，工单 38）按内容缓存实体编码器的输出（编码表）再提约 30%，默认引擎改为 64。

## 动机

一轮幕组采样约 47–54 分钟，采集进程（驱动进程里收帧 → 解包 → 前向 → 发回的串行链）是唯一瓶颈：v12–v16 第 2、3 次迭代的第三幕波等采样进程只 8 s / 2,132 s，前向 1,450 s（68%）、解包 427 s（20%）、其它 197 s（9%）、发回 49 s；每次前向平均 15.0 条决策、31 ms，485 决策/秒（32 引擎）。重叠模式被否决（[27](27-overlap-mode.md)）后，缩短采样只能靠采集链本身。

## 做法与结果

### 采集分段计时与引擎数（工单 15）

- 做法：`Samplers.timing` 按轮记 `passes`、`decisions_per_pass`、`seconds_per_pass` 与等待、解包、选择、回传各自的秒数；`scripts/collector_timing.py` 只打第一波（到第二幕），按引擎数各跑一次。
- 实测（v11，第一波 200 段，机器空闲）：32 引擎 381 决策/秒、每次前向 13.8 条、36 ms，选择（前向加拷回）27.2 ms（75%），等采样进程 4%；64 引擎 538 决策/秒、23.5 条、44 ms，等待 11%，内存多约 4 GB。
- 当时的判断：每次前向约 27 ms 是固定开销，建议 `--workers 64`，128 引擎预计再 +20–30%。
- 为什么没用：第一幕的帧短，固定开销占主导；第三幕的帧长，发射随决策数涨（见下文 S1），64 引擎反而不如 48。

### 主机同步点（工单 22 阶段 02）

- 做法：`torch.cuda.set_sync_debug_mode` 定位一次前向里的同步：解包的 4 次可分页拷贝、解包末尾 1 次、`_actions` 1 次、最后拷回 1 次。
- 实测：前 5 次发生在 GPU 还没排上重活时，代价小；`_actions` 那次之后只剩决策头。
- 为什么没用：小批时瓶颈是 CPU 发射本身，不是同步。不改。

### 全局层整栈 inductor 编译（工单 22）

- 做法：24 层全局层整栈 `torch.compile`，与逐块编译、整栈 CUDA graph 对比（`scripts/stack_variants.py`，只计全局层加决策头，中位 ms）：

  | 决策数 | 逐块编译 | 整栈编译 dynamic | 整栈 CUDA graph |
  | --- | --- | --- | --- |
  | 8 | 6.2 | 15.1 | 3.0 |
  | 16 | 10.7 | 8.2 | 3.6 |
  | 24 | 8.8 | 7.9 | 4.4 |

- 为什么没用：整栈编译的 greedy 对数概率偏差 0.04–0.09，太大，且不比 CUDA graph 快。改为手工录 eager 在补齐批上发射的核函数（见“最终有效的做法”）。

### 实体编码器 `torch.compile`（工单 22、25 B′、30）

- 工单 22：`dynamic=True`，24 条决策一次 pass 31.8 → 24.4 ms（−23%），8 条几乎不变；greedy 对数概率与未编译相差最多 5e-3。块再编译（`scripts/encoder_compile_check.py`）再快 10–15%，但 greedy 选择变 0.2–0.6%、偏差平均 1e-3。否决理由：采样用编译版、训练重放用 eager，两边不一致给比值加噪，同策略核对的 1e-3 容差要放宽。
- 工单 25 B′（第三幕帧）：16／32 条 22.3 → 21.0、47.5 → 43.3 ms，greedy 对数概率偏差 0.011／0.008，排除。
- 工单 30：两边都用编译版时数值可行。96 条探针决策各放进两个不同的 16 条批：

  | | eager | 编码器编译 |
  | --- | --- | --- |
  | 同一决策跨批的对数概率差（均值／最大） | 8.7e-4 / 7.8e-3 | 5.8e-4 / 4.3e-3 |
  | 同一决策跨批 greedy 一致率 | 97.9% | 100% |
  | 编译版对 eager：对数概率差（均值／最大） | — | 1.0e-3 / 5.0e-3 |
  | 编译版对 eager：greedy 一致率 | — | 96.9% |
  | 一次前向 32 条（全局层已图化） | 24.1 ms | 19.7 ms |

  但带热身的采集 A/B（32 引擎、第三幕，先打 160 段热身再计时 320 段）：eager 618 决策/秒、每次前向 22.2 ms、13.7 条；编译版 563（−9%）、21.9 ms、12.3 条；热身轮 57 s 对 124 s。热身后每次前向的发射只少 0.7 ms（13.7 → 13.0），被 dynamic 形状的守卫与符号形状处理吃掉。不带热身的第一次探针更差：32 引擎 353（改前 509）、48 引擎 442（改前 560）。训练步的编码器编译（`joint_update_timing.py --compile-encoder`）跑了 32 分钟没出第一批结果、GPU 利用率 9%：训练微批每步形状都不同，反复重编，手工结束。
- 为什么没用：隔离微基准的收益到真实负载被守卫与重编吃掉；训练侧根本编不完。

### 采集线程优先级 nice（工单 25 方案 A）

- 原预期：CPU 争用占真实与隔离差距的大半，+25–35%。
- 实测（v14，round-3 第三幕帧续打，32 引擎）：nice 0／nice 5 每次前向 33.7／33.0 ms，14.1／14.3 条，419／432 决策/秒，只差 3%。
- 为什么没用：差距来自第三幕的帧更长，不是调度争用。

### 实体编码器 CUDA graph（工单 25 方案 B）

- 原预期：编码器是一次前向里最大的一块，pass −7–10 ms，+30–45%。
- 实测：`encoder_profile.py` 显示编码器 GPU 核时间约为墙钟的 75% 以上、每次约 620 个核函数，是算力受限，不是发射受限。`encoder_breakdown.py`：大程序组的 `fields()` 16／32 条 7.2／25.0 ms，占编码器一半以上；`program_padding.py`：程序组里有效节点行只占 28.9%、有效字段 6.1%（节点长度集中在 5–16，全补到 32）；只算有效行 2.2／4.1 ms。
- 为什么没用：图化省的是发射，编码器的时间花在补齐行上的算力。取代它的是程序节点字段紧凑化 D′（见“最终有效的做法”）。

### 实体编码器 bf16／TF32（工单 25）

- 实测（`encoder_precision_check.py`，采样侧）：fp32／tf32／bf16 在 16 条时 26.5／27.5／20.9 ms，32 条时 50.6／52.5／47.3 ms；bf16 的同策略跨批噪声 0.0018（现 0.0009）、greedy 选择变 0.3–0.6%。
- 为什么没用：收益小、数值变差。实体编码器保持 FP32，是为了对数概率不随批组成抖动。训练侧的 TF32 见 [30](30-update-step-speed.md)。

### 多个采集进程（工单 25 方案 E、工单 30）

- 工单 25 时不做：驱动已初始化 CUDA，要做就得回到刚删的采样侧结构。
- 工单 30 的零改动探针（同时跑 N 个 `collector_timing.py`，各一份模型、各 48/N 个引擎，热身后计时，第三幕续打）：合计 1×48 = 696、2×24 = 725（+4%）、3×16 = 642（−8%）决策/秒。每个进程的每次前向没有因引擎减半而变短（29.6 → 29.6 → 34 ms），解包 6.5 → 8.3 → 11.1 ms，前向 17.8 → 18.1 → 20.9 ms。机器负载 15，不是 CPU 争用。主机内存每多一个采集进程少约 1.8 GB（可用最低 15.3 → 13.5 → 11.5 GB）；显存两进程合计 10.7 GB。
- 为什么没用：多个 CUDA 上下文的核函数在 GPU 上不重叠，按时间片轮转（WSL2 没有 MPS，`nvidia-cuda-mps-control` 不存在，Compute Mode Default）。

### 采集两批在飞 S2（工单 29）

- 原预期：pass 从“解包 + 前向 + 其它”串行变成 max(CPU, GPU)，+25–35%。
- 做法：`wire.unpack` 经两套交替的钉住暂存缓冲异步拷；`_collect` 在上一批的前向还在 GPU 上时收取、解包、发射下一批；`_Timing` 多 `syncing_seconds`。
- 实测（第三幕续打，320 段、约 5.8 万决策；秒为整轮合计）：

  | | 决策/秒 | 每次前向 | 条/次 | 等待 | 解包 | 发射 | 等 GPU | 回传 | 其它 |
  | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
  | 改前，32 引擎 | 509 | 26.6 ms | 13.5 | 7.4 s | 26.6 s | 66.8 s | — | 2.5 s | 10.3 s |
  | S2，32 引擎 | 426 | 22.0 ms | 9.4 | 7.5 s | 45.5 s | 71.4 s | 2.8 s | 2.5 s | 9.2 s |
  | S2，48 引擎 | 460 | 29.7 ms | 13.7 | 11.1 s | 47.6 s | 54.0 s | 2.4 s | 2.4 s | 10.4 s |

- 为什么没用：`syncing` 每次前向不到 0.5 ms，GPU 几乎从不被等；改前的 26.6 ms 里等 GPU 只有约 4–5 ms，采集进程本来就是主机发射受限。两批在飞把同样的主机工作切成更多更小的前向（4,276 → 6,300 次），每次带的决策少三成，吞吐 −16%。不存在比“把到达的全部决策合成一次前向”更好的分批。回退。

### 解包改写：主机侧 numpy S3′ 与三个合并原型（工单 29、30）

- S3′（工单 29）：在 numpy 里拼接、掩码、补齐，按 dtype 合成三个缓冲各钉住、异步上传一次，数值逐位相同。32 引擎 509 → 465 决策/秒（解包 6.2 → 9.4 ms/次），48 引擎 560 → 481（7.1 → 15.6 ms/次）。回退。
- 工单 30 先计时：第三幕 16 条一次解包 4.2 ms，160 个核函数 + 16 次拷贝 + 8 次 `cudaStreamSynchronize`（`aten::add` 38 次、`cat` 31、`arange` 12、`repeat_interleave` 6、`masked_scatter_` 12）。三个原型都与原版逐位相同：
  - 原型 1，主机 numpy 拼接：32 引擎 494 决策/秒（−20%），解包 10.2 ms；48 引擎 521、16.9 ms。隔离测量只要 4.2 ms。
  - 原型 2，设备拼接 + 按字段名布局去掉 31 次 `cat` + 同掩码合并散布 + 逐次 `pin_memory()`：设备事件 167 → 89、同步 8 → 0，但隔离主机时间 4.3 → 9.5 ms，采集 492，解包 9.9 ms。
  - 原型 3 = 原型 2 改回可分页拷贝：主机时间 4.2 → 3.4 ms，采集 602 对 eager 618，解包 5.5 → 5.05 ms。
- 为什么没用：numpy 的花式索引、布尔掩码与钉住拷贝在几万到几十万元素上比设备上四十次小算子更慢，且 32 个引擎与采样进程占着 CPU 时不可靠；逐次 `pin_memory()` 要向驱动申请钉住页，比可分页拷贝加同步贵；少 78 个核函数只值约 0.5 ms，一次前向 22 ms 的 2%。现状的设备侧小算子加可分页拷贝已是三种写法里最快的。原型已删。

### 编码器分桶 S4（工单 29）

- 设想：程序组分四桶（≤4、≤16、≤32、更大；第二组 696／1,335 个程序全补到 64 个节点，节点行只有 20% 有效），token 字段按宽度分桶（≤8、≤16、全宽；有效 33%）。
- 为什么没用：省的是 GPU 时间、加的是每次前向的发射次数，对主机受限的采集只会更慢；训练侧 token 字段的 `fields()` 只占步的百分之几。不做。工单 25 阶段 02、工单 26 E7 的 token 字段紧凑化也一直未做。

### 引擎 32 → 48 → 64 S1（工单 29）

- 原推算：D′ 之后 pass 随决策数涨得慢，48 引擎约 890 决策/秒，+35–45%。
- 实测（第三幕续打，改前代码，同一探针；主机分段为每次前向的毫秒数）：

  | 引擎 | 决策/秒 | 每次前向 | 条/次 | 等待／解包／发射（含等 GPU）／回传／其它 | 最低可用内存 |
  | --- | --- | --- | --- | --- | --- |
  | 32 | 509 | 26.6 ms | 13.5 | 1.7 / 6.2 / 15.6 / 0.6 / 2.4 | 17.7 GB |
  | 48 | 560（+10%） | 35.8 ms | 20.1 | 2.3 / 7.1 / 20.0 / 1.2 / 5.3 | 14.9 GB |
  | 64 | 548 | 49.0 ms | 26.9 | 4.2 / 8.3 / 23.3 / 1.6 / 11.6 | 13.8 GB |

- 发射时间随决策数涨（编码器的核函数数量随程序组、token 数涨），“其它”（收消息、反序列化）随引擎数涨得更快，64 引擎已被抵消。推算的 +35–45% 实测只有 +10%。采用 48：每多 16 个引擎采样期多占约 4.5 GB，真实运行采样期可用内存约 14 → 9.5 GB，仍在看门狗 2.5 GB 之上；每对“引擎 + 采样进程”约 280 MB。

### flex_attention 稀疏关系偏置（工单 30）

- 做法：`flex_bias_bench.py`，真实训练微批（404 行 × pad 128、3.6 万 token、5.6 万条边），24 层前向加反向。

  | 变体 | 时间 | 额外显存 |
  | --- | --- | --- |
  | 稠密 `relation_biases` + SDPA（现状） | 36.0 ms | 2.28 GB |
  | flex，无偏置（核函数下限） | 15.1 ms | 0.73 GB |
  | flex，score_mod 查可学习关系表 | 934 ms | 0.73 GB |
  | flex，每行一份表副本再求和 | 42.5 ms | 0.79 GB |

- 每对 token 最多 1 条关系，score_mod 一个槽位即可。查可学习表的 934 ms 是反传把 2,600 万个 (b, h, q, k) 的梯度原子加进 3,072 × 4 个格子的争用；每行一份副本把争用分散 404 倍。第一次测得 920 ms 是每层一个新的 score_mod 闭包导致重编，不作数。关系表梯度与稠密路径余弦 1.0，差在第 0 行（flex 里无关系的对也落到第 0 行，生产中把它的梯度置零即等价）。输出差均值 1e-3、99.9 分位 0.06、最大 0.28（|输出| 均值 3.2），是 bf16 核函数之差。
- 显存账：20M（4 头）在 `pair_budget` 1,678 万对时偏置最多 3.2 GB；200M（12 头）最多 9.7 GB，探针微批形状 3.8 GB。
- 为什么没用：20M 上它不是速度项，是显存项（约 ×3）。采样侧保持 SDPA（小批上 flex 没有优势、还要进 CUDA graph）。用户 2026-10-18 定：留到转 200M 时按显存需要再做。

## 最终有效的做法

| 做法 | 提交 | 实测 |
| --- | --- | --- |
| 各全局层的关系偏置并排一次建出 | `f2c678d` | 与下一项合计：v11 第一波，32 引擎 381 → 564 决策/秒（+48%），64 引擎 538 → 657（+22%） |
| 采样时全局层按桶补齐后作 CUDA graph 重放（`GraphedStack`） | `3f536b3` | 8／16／24／32 条一次 pass 19.2 → 12.1、22.8 → 20.8、30.1 → 28.8、46.5 → 36.2 ms；greedy 选择全同，对数概率偏差平均 1.4e-4、最大 8e-3 |
| 程序组的字段只装真实节点（D′） | `525b528` | 第三幕编码器 16／32 条 19.1／35.1 → 8.0／14.8 ms；32 引擎第三幕续打每次前向 33.7 → 24.5 ms，419 → 564 决策/秒（+35%）；数值逐位相同 |
| `--workers 48` | 文档与示例（工单 29） | 第三幕 509 → 560 决策/秒（+10%） |

真实运行的对照：v12–v16 第 5 轮（D′ 之后）第三幕波 601 决策/秒、每次前向 23.3 ms，前几轮 485 决策/秒、31 ms；整轮采样 2,483 s 对前四轮 2,780–3,145 s，约 −14%（[32](32-v12-v16-plateau.md)）。

## 原因分析

- 稳态模型（工单 25）：等采样进程几乎为零，一个引擎的周期 ≈ 自己的一步 t_e + 2 × pass，反推 t_e ≈ 4 ms；每次前向带的决策数 ≈ 引擎数的一半，吞吐 ≈ K / (2 × pass(K/2))。不加引擎，每次前向就带不了更多决策；故意等几毫秒攒决策只会拉长周期。
- 采集进程是主机发射受限：每次前向约 20 ms 的发射与解包，GPU 只占几分之一。省 GPU 时间的改法（分桶、两批在飞、编码器图化）都无效；省发射的改法（编译）又被 dynamic 形状的守卫与重编吃掉。
- 多数原预期建立在“GPU 是瓶颈”或“CPU 争用是瓶颈”的假设上，与实测相反。

## 结论与后续

- 采样侧眼下能动的只有引擎数；再往上只剩减少编码器的核函数数量。（2026-10-19 更正：这里漏了“不重复计算”。同一局里 98% 的程序、96.6% 的实体与更早的决策内容相同，工单 38 把实体编码器的输出按内容留在表里，第三幕 +26%（48 引擎）、+33%（64 引擎），见 [play 编码表](../implementation/play.md#采样进程分工)。）
- 一轮的对局数（每角色种子数的五倍）不宜少于引擎数，否则一轮末尾引擎空转；实现文档原写的“多几倍更省”是经验说法，没有留下实测。
- 已删或回退的代码：S2、S3′、三个解包原型、编码器编译的探针脚本都已回退或删除；`collector_timing.py`、`joint_update_timing.py`、`flex_bias_bench.py`、`encoder_breakdown.py` 留在工单目录供复跑。

## 教训

- 先 profile 判断“发射受限还是算力受限”，再决定图化还是减少算量。
- dynamic 形状的编译在隔离微基准里的收益，到真实负载会被守卫与重编吃掉；A/B 必须带热身轮。
- 主机侧 numpy 在几十个引擎与采样进程占着 CPU 时不可靠，隔离测量会误导。
- 加引擎的收益要在最长的那一波（第三幕）上测，第一幕的数会高估。
- 多 CUDA 上下文在没有 MPS 的 WSL2 上不并行。
- 先问相邻两次前向的输入有多少相同、能不能不算，再问怎么算得更快：这里的提速尝试都在第二个问题上。
