# 结构选项开关、逐项消融与宽度扫参

- **时间**：2026-10-10 加入八项默认关闭的结构选项；2026-10-11 用户决定不消融、不扫宽度，同日 `c689a79` 把其中七项定为唯一结构。
- **来源**：`.scratch/a0-training-baseline/spec.md`（2026-10-10、10-11 两条 Comments）；`c689a79` 提交信息；`db6648d:ARCHITECTURE.md`「网络结构」「取舍」；`.scratch/a0-training-baseline/issues/20-200m-training.md`（2026-10-11「结构定为一种」）。
- **状态**：被否决，消融与扫参都没做；七项选项全开成为网络本身。

## 动机

2026-10-10 目标规模由 1B 改为约 200M（`configs/rtxpro6000-200m.json`：768×24、FFN 2304、局部 384）。宽度扩到三倍、头数由 4 增到 12，注意力 logit、残差流尺度和 Muon 学习率是否随宽度漂移都没测过。于是把几项通行的稳定化做法做成开关，20M 配置不变，打算逐项确认哪些该开。

## 做法

- 八项选项，默认关闭：QK-norm、深度缩放初始化、决策头 QK-norm、逐层关系偏置、字段注意力、MLP 价值头、无线性偏置、RMSNorm。
- 各项的作用（`db6648d:ARCHITECTURE.md`）：注意力的 query 与 key 归一化，限制 logit 随宽度和学习率增长；残差分支输出投影的初始权重缩小 1/√(2L)，让残差流尺度与深度无关；每个全局层一张关系偏置表；实体字段求和前一层字段间注意力；决策头的查询与动作键同样归一化；线性层无偏置、归一化用 RMSNorm，是通行做法、少一批小算子。
- 计划：在 20M 上逐项消融；在宽 256 与 512 上各跑多条，扫 Muon 学习率的宽度迁移。

## 结果

没有运行，没有实测数字。

- 2026-10-11 用户经逐项访谈确认：不消融结构选项、不扫宽度。
- MLP 价值头随整局 PPO 一起删除（[12](12-outcome-ppo.md)），剩七项。`c689a79` 把七项全开定为 `architecture_version` 3：“相同种子下与旧代码七项全开时的权重和输出逐位相同”。两份配置是同一结构的两个尺寸：20M 约 21.30M，200M 约 195M。
- 结构版本 2 的检查点（`runs/bootstrap-20261008/init-v5`、`trained-v8-potions`，以及临时目录里做冒烟的 200M 检查点）载入时按版本报错，20M 要从头 `init` 与 BC。
- 旧结构 20M 的 2,000 局基线（11.05%）只能当参照数字，新结构要自己跑基线才能做配对比较。

## 原因分析

“逐项消融要八次以上的 20M 训练，宽度扫参要在 256 与 512 各跑多条；两者都换不来路线上的信息。”（`db6648d:ARCHITECTURE.md`「取舍」）当时路线本身（示范、求解器标签、critic、AWR）都没验证过，结构上的取舍排在后面；七项都是通行做法，“不逐项消融，效果由整体结果判断”。

## 结论与后续

- 网络只有一种结构，开关、`from_architecture` 与 `--architecture` 已在 `c689a79` 删除。现状见 [architecture 全局骨干](../architecture.md#全局骨干) 与 [network 配置](../implementation/network.md#配置)。
- Muon 学习率不扫宽度，改为在 200M 本身上用 `1e-3` 与 `5e-4` 两条各 2,500 次更新的探针确认（[network 优化器与学习率](../implementation/network.md#优化器与学习率)）。探针至今没跑，见 [14](14-200m-training.md)。

## 教训

- 路线没验证之前，结构消融的信息价值低于路线验证。
- 改结构会让旧检查点载入失败，也让旧基线失去配对比较的对象；改之前先算这笔账。
