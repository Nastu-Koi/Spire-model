# 采样与更新的代码层提速

- **时间**：2026-10-21
- **来源**：`.scratch/joint-training/issues/throughput.md`（42，承接 41）；探针原始输出在 `.scratch/joint-training/assets/42-timing-*.json`；探针脚本 `collector_timing.py`、`joint_update_timing.py`、`update_timing.py`（`.scratch/joint-training/scripts/`）
- **状态**：部分有效。采用的做法：采样进程只给新内容建字段张量，`clean_frame` 不再整帧深拷贝，观察不重洗已洗过的帧，实体字段缓存的键改用 `repr`，引擎关掉 .NET 的按剖析重编译与后台垃圾回收，热路径上的 JSON 换成 orjson。采用后，64 引擎续打第三幕从 952 提到 1,275 决策/秒（单次对比）。其余尝试见总表。

## 动机

v55–v62 起用 64 引擎。采样时整机 CPU 饱和（负载约 60，空闲 8.7%）。一次迭代里采样约 1,150 s，更新约 1,300–1,690 s。工单 42 先只读代码列出候选，用户要求先补计时（`main/env/clock.py`、`Samplers.timing` 的 `collecting`／`sampling`、更新记录的 `shapes`），再逐项分析修改。

## 改动前的计时

计时条件：64 引擎，续打第三幕 800 段；检查点为 v55–v62 iteration-0007；存档取 v35 round-1 的第二幕存档（round-7 的存档已被清理）。

- **吞吐**：952 决策/秒。
- **采样进程**：自己的时间 t_e 为 33.5 ms／决策，其中：
  - 引擎 9.9 ms
  - collate 与掩码 8.2 ms
  - `clean_frame` 5.1 ms
  - observation 4.3 ms
  - 段交出 2.0 ms
- **采集进程**：每次前向 21.2 ms，带 20.2 条决策，其中解包 5.1 ms、编码器发射 5.1 ms、等 GPU 与拷回 2.2 ms。

单进程、无争用时的单项开销只有上面的三到四分之一：observation 1.4 ms、collate 1.9 ms、`clean_frame` 1.5 ms（其中深拷贝 1.0 ms）。引擎每步墙钟 2.1 ms，引擎进程却用掉 3.7 ms CPU。

## 原因分析

- **采样的 CPU 账**：64 个采样进程和 64 个引擎跑在 16 核 32 线程上，每项单进程开销的墙钟被放大三到四倍。省下的 CPU 既缩短 t_e，也减轻采集进程被抢占。加进程（80 引擎、每进程两引擎）和调优先级，都只是在分同一份 CPU。
- **改完之后**：引擎周期约 47.5 ms，其中 30 ms 在等采集进程。采集进程每次前向 22.5 ms 里，解包、收发、发射都在饱和的 CPU 上进行；GPU 平均利用率约 31%。C2 省下的主机发射时间变成了等 GPU 收尾和每次前向少带的决策，吞吐没动。采集线程独占一个物理核后每次前向仍要约 22 ms，可见它慢在自身的活（解包、发射、收发的系统调用），不是被采样进程抢走 CPU。
- **补齐率**：更新时全局层的补齐率低，第三幕 token 只有 54%、注意力对只有 30%。但把微批切小，每多一个微批就多约 20 ms 固定开销，补齐率又只是慢慢上升（400 万时注意力对 53%），两者抵消。
- **T1 不做的原因**：每个样本约 1.35 ms。三波合并每步能省两次固定开销，但第一、二幕的短行会被补齐到第三幕的长度，按每样本成本估算要多出约 70 ms，两相抵消；合并后一个微批 512 行，显存约 77 GB，逼近 80 GB 的上限。
- **更新步主机侧的实情**：profile 显示，WSL2 上 `cudaLaunchKernel` 平均每次 101 µs，另有命令缓冲刷新（Buffer Flush）。GPU 核函数时间约 0.42 s／步，而一步要 0.8 s。`relation_biases` 的自身耗时里有一大块是在等发射队列，不是分配器：分配没有重试，也没有归还。

## 结论与后续

- 采用的做法写进了 implementation 文档：encoding（P1、P2、P3、P4）、play（采样进程的用法、计时项、orjson 存帧）、env（`RUNTIME_SETTINGS`、orjson 解析引擎回复）。计时留在代码里，供每次正式运行记账。
- 采样侧剩下的大项是采集进程的解包与收发，试错 [29](29-collector-throughput.md) 里已否决多种写法。改完之后采样进程再快，引擎也只是多等采集进程（P5 就是这样）。
- 更新侧这一轮没有找到可用的提速；补齐浪费要靠变长注意力解决，而它和稠密关系偏置冲突，flex 实现更慢（试错 [30](30-update-step-speed.md)）。

## 教训

- 先补分段计时再动手。只读代码时估计 collate 几毫秒、清洗约 1 ms，实测在饱和机器上分别是 8.2 ms 和 5.1 ms；引擎反而只占 t_e 的三成。
- 改 .NET 运行时开关前要比对状态哈希。等待帧的出现时机本来就随运行变化，比较时要跳过等待帧，并把每个到达的状态都计入。样本要走到商店、事件、宝箱。
- 主机受限时，省下的发射时间可能只是变成等 GPU，要以吞吐为准。同配置的跑间差约 ±5%（更新步）到 ±10%（采样），小于这个量的改进要多跑几次。
