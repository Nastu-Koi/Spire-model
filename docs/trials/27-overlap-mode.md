# 采样与更新并行的重叠模式

- **时间**：2026-10-17（13:24 加入，16:59 删除）
- **来源**：`.scratch/joint-training/issues/throughput.md`（20）；提交 `f8bbe24`、`dacfd3f`（加入与启动修复）、`e4530a9`（删除，含 `docs/architecture.md` 的删改）
- **状态**：被删除。第一次真实迭代就把主机内存压到看门狗线边缘、显存被两进程占满，更新步慢十倍。用户此后不再考虑以内存换时间的并行方案。

## 动机

GRPO v7–v11 那次运行（`runs/grpo-20261017/train/v7-v16`）一次迭代约 95 分钟：采样 48–58 分钟、更新 37–42 分钟、优势与清理约 3 分钟，两步串行。采样期 GPU 几乎空闲（20M 网络每次前向约 30 ms、带十几条决策），更新期引擎休息、CPU 大半空闲。期望第 N 轮的更新与第 N+1 轮的采样同时进行，一次迭代接近 max(采样, 更新)，约省四成。

## 做法

- 两种模式，启动时切换：`--overlap`（`Settings.overlap`），默认关。
- 采样侧（新模块 `main/overlap.py` 的 `SamplingSide`）：驱动在载入策略、初始化 CUDA 之前 fork 出来，持自己的模型对象与 `Samplers` 池；每份任务按归档路径把权重就地载入（`checkpoint.load_weights`），做一轮幕组采样和／或一次评估，结果经管道回报。
- 流水线：第 N 次迭代做优势(N) → 发任务“用 P_{N−1} 采第 N+1 轮，到期则评估 P_{N−1}” → 更新(N) → 收结果、记入 `state.json` → 清理(N)。数据对被更新的策略晚一个版本，比值仍用采样时记的 `old_log_prob`，属一步离策略，由裁剪与 KL 兜住。
- 归档多留一代（采样侧还要读 P_{N−1}）；第 N−1 次的评估在第 N 次迭代才到，`history.jsonl` 标 `eval_iteration`。
- 预估内存：采样期约 10 GB（32 引擎）到 16 GB（64 引擎），训练期加载进程约 7–9 GB，两份模型进程各 2 GB，合计约 21–29 GB；机器 31 GB。
- 试跑：v11（`train/v7-v16/policy/iteration-0004`）起，KL 参考 v11，32 引擎，每角色 25 种子，n = 4、m = 4／8，κ = 0.1，`configs/learning-rates-grpo.json`，熵下限 0.45；输出 `runs/grpo-20261017/train/v11-overlap`，看门狗阈值 2.5 GB，另有每 30 秒的各类进程 PSS 记录。

## 结果

- 合成引擎测试没覆盖的两处在真实启动时暴露：
  1. `configure_runtime` 在命令分派前就调 `mem_get_info`、`cudnn.version()`，CUDA 已初始化，采样侧按设计拒绝 fork。改为驱动在 fork 之后才预留 GPU（`configure_gpu`）。
  2. 采样侧载入策略时没带学习率文件，v11 检查点的学习率是 GRPO 文件的、profile 是 BC 的，严格续训拒绝。
  另：采样侧从跑过 torch 运算的进程 fork 出来后，第一次前向死锁在父进程的 intra-op 线程池上，`torch.set_num_threads(1)` 解决。
- 第三次启动 15:04，round-0 同步采样 51 分钟（v7–v11 为 48–58 分钟）。
- 更新 0 与第 1 轮采样并行后：前 600 步每步 1.1 s（单独训练时 0.425 s）。16:05 第 1 轮进入第三幕起每步 10.5–11 s，`wait_seconds` 0.05 s（不是读取端）；GPU 显存 96 GB／97.9 GB 占满、利用率 11%，驱动与采样侧各 100% CPU。按这个速度一次更新要 7 小时。
- 主机内存：更新期读取进程约 9–10 GB 加采样侧第三幕约 11 GB，16:47 可用内存低至 2.89 GB（阈值 2.5 GB）。

## 原因分析

- 显存：两进程各按 `min(80 GB, free − 8)` 设预算，合计 160 GB，没有互相约束，分配器在物理显存耗尽边缘反复释放重试。采样侧的 `GraphedStack._capture` 每个形状各开一个私有内存池并 clone 一份输入；24 层关系偏置 [rows, 4, pad, pad] bf16 在 (32, 2048) 这一桶就是 25.8 GB，静态缓冲再加一份。第三幕的帧更长，新桶陆续捕获，显存随之涨满。同步运行里采样与训练在同一进程、共用缓存，所以没暴露。
- 主机内存：幕间通关率越高，第三幕的段越多，采样期内存本身就在涨；再叠加更新期的读取进程，内存注定是瓶颈。
- 修法本来有候选（两侧硬划显存预算、所有 graph 共用一个内存池、大 pad 的前向按偏置预算分块、`--workers 24`），但内存这一条无法靠代码绕开。

- 试跑目录改名为 `train/v12-v16`，round-0 的采样被沿用，改为串行续跑（[32](32-v12-v16-plateau.md)）。量采样前向显存的 `scripts/graph_memory.py` 没跑完就被否决。

- 现在采样、更新、评估在一个驱动进程里按顺序进行，见 [architecture 训练路线](../architecture.md#训练路线) 与 [learn 迭代驱动](../implementation/learn.md#迭代驱动)。

## 教训

- 这台机器上主机内存与显存是并行方案的硬上限；写代码前先算两侧峰值之和，并按训练进展（第三幕段数增多）留余量。
- 两进程共用一张卡时要硬划显存预算；CUDA graph 的私有内存池在单进程里看不出代价。
- 合成引擎测试覆盖不到 CUDA 初始化时机与严格续训，真实启动前要有一次小规模的真引擎冒烟。
